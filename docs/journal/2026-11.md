## 2026-11-26 03:20 — a `t_end` the editor could not read became the settings panel's, silently

Asked to establish what #199 actually costs a user — "does the solver reject it loudly, or does
something parse to a wrong number?" — and to work out whether the fix belongs here or in the
engine.

**#199 itself is loud, and that is a real finding.** Compiled `buck_converter` with `rload`'s
`R` replaced, against the committed bundle (`gsim-wasm` 0.6.2 at `5d4a83b`):

| `params.R` | netlist line | `notes` | `.PARAM` |
|---|---|---|---|
| `"{3 + 4}"` | `rload n_cout_p 0 {3 + 4}` | `[]` | none |
| `"{3+4}"` | `rload n_cout_p 0 {3+4}` | `[]` | none |
| `"Rload"` (with `params: [{Rload: 7}]`) | `rload n_cout_p 0 Rload` | `[]` | none |
| `"{Rload * 2}"` | `rload n_cout_p 0 {Rload * 2}` | `[]` | none |

and `general-simulator` 0.8.0 refuses all of them outright:

```
{3 + 4}   line 9: device 'rload' unexpected extra parameter '+' (device R takes exactly one value)
{3+4}     cannot stamp element 'rload': unsupported scalar expression '{3+4}'; use a number or symbol
Rload     Evaluate(MissingSymbol("Rload"))
```

So that half is a failed run with a message in the solver's vocabulary, not a wrong number. It
is still a real bug — the spec says the loader evaluates §5.2, the inspector shows a resolved
number beside a field that cannot compile — and it belongs in the **engine**: `loadDocument` is
the loader §5.2 names, and Invariant 0a says the editor does not get a second copy of the
compiler. Filed as `GLODI-Engineering/gsim-core#94`, with two further gaps found in the same
pass: a cyclic `params` table is accepted where §5.2 says cycles are rejected, and §5.3's
analysis-directive fields are accepted unevaluated. Reaching users needs that change plus a
rebuild of this repo's committed bundle.

**The wrong number is on this side of the line, and it is #244.** §5.3 permits an expression in
`t_end`/`t_step`. `loadDocument` accepts `"t_end": "{T_sim}"` without a word, and then
`shell/run.ts`'s `namedAnalysis` read it as

```ts
tEnd: typeof analysis.t_end === "number" ? analysis.t_end : settings.tEnd,
```

so the run used the Simulation settings panel's own value and went ahead. Measured, with the
sheet declaring `T_sim = 0.002`: the run went out at **`tEnd = 0.01`**, five times the window
the document declares. With `t_step: "{T_sim / 100}"` it went out at **`tStep = 1e-5`** against
the document's `1e-7` — a hundred times coarser, which is exactly the once-per-switching-period
aliasing #193 exists about. Nothing in the output, the Problems panel or the toast said which
number won.

The comment on those two lines said the fallbacks were "for a malformed document". That was
true when it was written; §5.1 and §5.3 made such a document well-formed, so the one case the
fallback was never meant to cover became the main case it covered.

`timingForAnalysis` in `shell/analysis-defaults.ts` now returns the declared numbers or a
refusal naming the analysis, the field and the value as written, and `triggerRunAnalysis`
reports it from the editor and does not call the host. The fallback stays for the case it was
written for — a document with **no** `simulation` block, a genuine absence rather than a value
being misread — `stepForDocument`'s refinement included.

Reproduced before the fix: `shell/run-analysis-timing.test.ts` had three of its five cases red,
each printing the substituted number in the request it should never have made.

**Verification.** `pnpm biome check .` 0 errors / 112 warnings (the baseline, measured against
`main` in the same run), both typechecks, `pnpm test` (frontend 1,598 passed / 8 files skipped;
extension 146 passed), `scripts/check-invariants.sh`, `check-examples --check`, `check-keymap`,
`check-waveform-wasm-fresh`, `check-gsim-wasm-fresh --check`, and `e2e --project=chromium`.

**Known red, and not from here.** `check-gsim-wasm-fresh --check --against-engine` reports the

## 2026-11-25 23:40 — the toolbar fits, New Schematic is reachable, and a code block opens its own file

Three things the owner reported after using the editor, filed as #210, #211 and #212.

**The toolbar ran out of width and truncated (#210).** `.gs-toolbar` was a hardcoded `#0f172a`
slate bar 54 px tall whatever theme VS Code was in, and every button stacked a text label under
an 18 px icon inside 40x44 — about double VS Code's own metrics in both directions. Measured in
a real window: the row wanted 1,100 px and got 945, so the last control rendered as "Rotat…" and
the rest sat behind a 6 px scrollbar, which is a thing to discover rather than a thing to use.

Two changes, and both were needed. The labels became tooltips and accessible names, which is
where the height went — 54 px to 30 px, buttons 44 px to 24 px, component previews 56x44 to
34x24 — and the colours now come from the workbench (`--vscode-editorGroupHeader-tabsBackground`,
`--vscode-toolbar-hoverBackground`, `--vscode-inputOption-active*`), so the bar is dark in a dark
theme instead of being navy in both. The one label kept is Run's: someone opening the editor for
the first time has to be able to find the button that simulates.

That alone is not reachability, so `shell/ToolbarOverflow.tsx` measures the row and moves what
still does not fit behind a `⋯` menu. It works on the row's real DOM children rather than on
React children, because the row is assembled by three components and a fragment flattens in the
DOM but not in `React.Children` — so from `MainToolbar`'s side the whole schematic segment is one
child. The hidden controls stay in the DOM and the menu entry clicks the real one; every existing
selector (`.main-toolbar button[aria-label]`, `.schematic-toolbar__component`) keeps working.
Run carries `data-toolbar-pin` and never moves.

Measured afterwards in a real window: 1205 px pane — everything fits, no scroll; 706 px — nine
controls behind the menu, no scroll; 466 px — seventeen, no scroll, Run still visible in all
three. The first attempt still scrolled 21 px at 706, because the plan did not charge the row's
`gap: 2px` to each of twenty children.

**"New Schematic" existed and was unreachable (#211).** The command was contributed to
`commandPalette` and nowhere else, so "click the extension and there is no way to create a new
file" was an accurate description. It is now in `file/newFile`, on the Block Library's title bar
and in the Explorer's folder context menu, it seeds the Save dialog with a name and a sensible
folder, it refuses to clobber, and it takes a URI so the integration suite can drive it — a modal
Save dialog cannot be, and that is how the next thing went unnoticed.

**It wrote a zero-byte file, and that silently stopped the editor saving.** Opening one was fine:
`schematic-main.tsx` checks for empty text and starts from the default model. Reverting was not.
`revertCustomDocument` posts the file's bytes as `gsim/setDocument`, they reach
`loadDocumentTextOrReport`, `JSON.parse("")` throws, the document is recorded unreadable — and
while that is recorded `currentDocumentText()` hands the host back the original bytes, so every
later save is a no-op. Create a schematic, press File ▸ Revert, and the editor stops saving your
work without saying so. The command writes a real document now, and `document-load.ts` treats an
empty file as an empty schematic rather than a parse failure, which covers the ones a user made
with `touch` — which is exactly what they were doing while the command was unreachable.

**A scripted block opens its source (#212).** The reason the editor was moved into VS Code at
all. Double-clicking one now asks the host to open its `.c`/`.py`/`.m` beside the schematic, and
the language extensions attach by themselves. The webview says which paths it would accept and
what an empty file should contain; the **host** decides whether a path may be opened, because a
`.gsim_sch` may have been opened from anywhere and its parameters are untrusted text. Outside the
workspace it asks; outside the workspace it never creates.

`extensibility.cscript` turned out to be the awkward one: its parameter is `lib`, a compiled
library, not source. So that block had never shown the Inspector's "Read ports from source" at
all — the section required a `path` parameter the type does not have — and its source can only be
found by convention. `netlist/code-source.ts` holds that convention in one place and says so in
the Inspector; #222 is the real fix, in the engine. The stubs it writes are checked against
`code-ports.ts`, the parser the Inspector uses, so a created file is never one the editor then
reports as disagreeing with its own block.

Two more findings became issues rather than sentences here: #221 (the webview writes
`data-theme="light"` over whatever `followVsCodeTheme` decided, so a dark VS Code shows a light
canvas) and #222.

**Rebased onto #219, and the plate went with it.** The component previews shipped on a plate of
fixed near-white, because `symbol-drawing.tsx` inked every symbol in fixed colours and a dark
plate would have hidden it — a `--gs-symbol-plate` token with one value and a comment saying
why. #219 made that ink `var(--schematic-ink)` / `var(--schematic-paper)` for the Block Library,
so the toolbar sets the same two variables and the plate is gone: the symbols are drawn in the
row's own foreground on the row's own background, the same contrast as the icons beside them.
Measured in a real dark window, ink resolves to `rgb(140, 140, 140)` on `rgb(25, 26, 27)`, all

## 2026-11-25 23:20 — saving a new model stored a copy of it

`persistence.spec.ts:40`, the second of the three failures holding `e2e` red, asserts that a
save → reload → open round trip is byte-identical and it was not: `model-1` came back as
`model-1-copy-1795…` named "… Copy". #118 set out two readings — the app duplicates on open, or
the spec clicks a duplicate affordance — and asked which, by watching what the storage adapter
writes.

It is neither. The adapter duplicates on **save**, and the open path is faithful.

`StartupModal` renders one control per row and it calls `onOpen` → `openFileById` →
`adapter.load(ref)`, which returns the record as stored; there is nothing to misclick. But
`saveFile()` has no ref for a never-saved model, so the first Ctrl+S goes to `adapter.saveAs()`,
and `IndexedDbAdapter.saveAs` rewrote the document on the way in — `-copy-<timestamp>` onto
`model.id`, " Copy" onto `model.name`. Both callers are that first save and the `file.save-as`
command, whose toast says "Model saved"; neither asked for a duplicate.

The trace that settles it, taken by hand against a real Chromium:

```
--- after FIRST Ctrl+S ---
in-memory doc : {"id":"model-1","name":"probe-118-model"}
stored records: [{"key":"model-1-copy-…","docName":"probe-118-model Copy"}]

--- after SECOND Ctrl+S ---
in-memory doc : {"id":"model-1","name":"probe-118-model"}
stored records: [{"key":"model-1-copy-…","docName":"probe-118-model"}]
```

The second line is why nobody noticed. A second save writes the real document back under the
copy's key, repairing the name and `model.id` inside the record but not the key, so a user who
presses Ctrl+S twice sees no symptom at all. One who saves once, closes and reopens is working on
a duplicate from then on, and #118's predicted `Copy`, `Copy Copy` chain follows.

The document is now written through untouched and the ref is its own `model.id`, so key and
document identity stay in step. The timestamp suffix survives for the case the name implies — a
Save As over a model already stored, where a fresh key is the point — and nothing renames anything.
A storage adapter allocates refs.

`IndexedDbAdapter` had no unit test, which is why a 16-minute browser suite was the only thing that
knew. It has five now, each checked to fail against the old `saveAs` and pass against the new: the
old file restored, 5 failed; the new one, 5 passed. Checking that a new test fails first is cheap
and it is the only thing that distinguishes a test from a comment.
## 2026-11-25 23:55 — the load budget never loaded a model

CI answered a question I had closed too early. `perf.spec.ts`'s "load ≤ 200 ms for a 200-block
model" passed on main's measured run, so I treated it as outside the red gate and fixed only the
Quick Insert half of #105. It then failed on all three of my pull requests — including the one
that does not touch `perf.spec.ts` at all — at 275.9 ms, 339.7 ms and, on a retry of the same
code on the same runner minutes later, **687.6 ms**. A budget whose reading moves by a factor of
2.5 on identical code is not measuring the code.

#105 asked whether the 458 ms it once reported meant the budget had been set against a smaller
fixture than `__gensim_load_fixture` now builds, or whether loading 200 blocks had got slower,
and said to answer that before changing the number. It is neither, and the number was fine.

**The test never loaded a 200-block model.** It seeded the fixture and then timed
`page.reload()`. The harness restores nothing on boot, so the reload threw the fixture away —
measured directly, after it the sheet holds 0 blocks and `model.id` is back to `model-1`. The
200 ms budget was being held against a cold page boot of an *empty* document: HTTP fetch from the
Vite preview server, bundle parsed, React mounted. On a shared runner that is 226–688 ms and has
nothing to do with 200 blocks. Loading the fixture actually costs **2.3–16.6 ms**, and `App.tsx`
has been writing exactly that to `__gensim_perf.fixtureLoadMs` all along, where nothing read it.

Nor is page boot worth a budget on this surface: `index.html` is a dev/test harness and not a
product surface, and the editor ships inside a webview served from disk over `vscode-webview://`.
The preview server's HTTP boot time measures the test rig.

While I was in the file, the save budget turned out to be the same disease in the opposite
direction. It passed, and it never waited for a save: the `waitForFunction` holding it asked
whether `__gensim_last_save_ms !== undefined`, and `App.tsx` initialises that door to `0` on
mount, so the predicate was true on the first poll and the wait returned at once — with a
`.catch()` swallowing the timeout as "not exposed — approximate" for good measure. It was timing a
keypress round trip. It now clears the door to `undefined` first, which is a sentinel the app
never writes, so the wait waits and a save that does not happen fails loudly.

So all three of #105's budgets were reading the driver rather than the application, two of them
passing or failing for reasons unconnected to what they name. None of the three budget numbers
moved. Each was checked against a budget of 0 to confirm the assertion is live and reports a real
figure: Quick Insert p95 36.0 ms, save 17.7 ms, load 4.0 ms. The load test also asserts 200 blocks
are on the sheet, because without it a loader that did nothing would report a very fast load and
pass — which is the failure mode this repository has shipped four times.

## 2026-11-25 23:10 — the Quick Insert budget measured the test runner

`perf.spec.ts`'s "Quick Insert opens in ≤ 50 ms" was one of the three failures keeping `e2e` red
on `main`. #105 asked whether it was a stale locator or a real 2 s open, and said the question
should be answered rather than assumed. It was both halves of a stale test, and the app was never
slow.

**It pressed the wrong chord.** One `Ctrl+Shift+.` is the *prefix* of Quick Insert's chord, not
the chord — `keymap.ts` binds `Ctrl+Shift+.,Ctrl+Shift+.` — so the press only armed
`KeymapProvider`'s pending sequence and the dialog never came. That is the whole of the
`TimeoutError`. `SchematicPage.insertByName` has pressed it twice all along and its doc comment
spells out why, which is the part worth noticing: the knowledge existed in the action layer and
the spec predated it.

**And fixing the chord would have left it red.** `measure()` times `page.keyboard.press` and
`page.waitForSelector` in the runner's clock, so the number held against a 50 ms budget was mostly
CDP round trips. Driven correctly it reads p95 180 ms, median 114. The same open measured inside
the page is p95 18 ms, median 6. A budget on the application's latency has to be read where the
application is, so the keystrokes stay real — through the browser's input pipeline, which is what
keeps this a test of the shipped keymap — and only the clock moved into the page, from the keydown
that resolves the chord to the mutation that puts the dialog in the DOM. The budget itself did not
move. Writing that down because weakening an assertion to buy a green gate is the failure mode
this suite already has a history of, and pointing one at the thing it names is not that, but it
looks adjacent enough to deserve the paragraph.

**A dead keybinding fell out of it (#217).** A single `Ctrl+Shift+.` does not open the command
palette either, ever. `keymap.ts` declares `palette.command-azerty` and `App.tsx` handles only
`palette.command`; the alias id has exactly one occurrence in the repository, its own declaration.
So the dispatcher resolved the chord, waited out its 700 ms pending timeout, fired the fallback,
and the fallback was an id the switch dropped. On an AZERTY layout — where `.` needs Shift and
`Ctrl+.` cannot be typed, which is the entire reason the alias exists — the command palette had no
shortcut at all. Two lines, beside the quick-insert cases that always listed both spellings.

`check-keymap.mjs` and `gen-keybindings.mjs` were green throughout. They check that an id is
*registered*; neither asks whether it is *handled*. That is the same shape as the four gates this
repository shipped green while testing nothing, and it is #217's second checkbox rather than
something this commit fixes.

Three failures were red; this took one of them.

The owner used the Block Library panel and reported it as unattractive: "ports mismatch",

**What was actually wrong.** `SidebarItem` rendered the canvas `BlockSymbol` into a 56×40 box
at `width:100%;height:100%` with `overflow:hidden`. Three faults in one: that SVG is sized to
the block's bbox and draws its port stubs *outside* it (the canvas sets `overflow:visible`), so
every tile was cut off at the edge; percentage sizing threw the aspect ratio away, so a 200×40
boundary port and a 60×132 flip-flop came out the same oblong; and the body caption, 12 units
tall inside a box up to 80 units wide, shrank with the drawing until `abc/αβ0` was a smudge.

**The tile is now its own presentation.** `library/tile-art.ts` is pure geometry: a view that
contains everything the tile draws, a 7-unit port stump in place of the canvas's 20-unit lead,
and the caption handed back separately to be sized against the tile. `library/BlockTile.tsx`
draws it. A *labelled box* — which is every generic entry the engine ships, since the circles
and the triangle all have hand-drawn artwork — is drawn at the tile's proportions rather than
the engine's: `control.transform.clarke` is 80×66 because it has six ports, not because a
Clarke transform is squarer than a PID controller, and fitting those proportions left a box too
small for its own caption. Hand-drawn artwork keeps its aspect ratio, fitted with
`xMidYMid meet`.

**Theme.** `symbol-drawing.tsx`'s `STROKE`/`FILL` become `var(--schematic-ink, #0f172a)` and
`var(--schematic-paper, #ffffff)`. The canvas defines neither, so it renders byte-for-byte what
it did (checked against the reference screenshot of `buck_converter.gsim_sch`); the library
defines both from `--vscode-foreground` and `--vscode-sideBar-background`.
`component-symbols.tsx` had a second copy of the same two literals, which is how half the
artwork would have themed and half not; it now imports the one definition.

**Two "Step" rows.** The engine ships `signal.step` and `signal_flow.source.step`, and
`sinks.scope` and `signal_flow.sink.scope` — same `label`, different `equation_template`, both
`compilable`. Not duplicates to delete, and the catalogue is generated so the front end does not
get to edit it. `duplicate-labels.ts` qualifies a colliding label with its engine name, dimmed,
and only when it collides.

**Found on the way.** `.library-tree__items` was a `display:grid` with no
`grid-template-columns`, so its implicit column sized to the widest label and the panel scrolled
sideways. The row's accessible name was a run-on of the symbol's port labels ("Stepout port,
signal, outStep"); it is now an explicit `aria-label`. And `familyKey` groups

### "It was impossible to draw a line and touch a line"

Correct, and worth recording precisely: **wire tapping exists on `main` and is
not in `v0.2.0`**, which is what is installed. `wire-tap.ts` landed 2026-11-09.
The feature was reported as missing because the released build does not have it.

### The ideal transformer, and the solver bug under it

An ideal transformer is now a reusable `.SUBCKT` — a VCVS, a 0 V sense source
and a CCCS — placed as **one block** with `p1 p2 s1 s2`.

It could not have been, until today. An `F`/`H` card names the voltage source
whose branch current controls it, and that name is scoped to the body it is
written in. `general-mna`'s flattening prefixed every element name with the
instance path and left the reference alone, so `F1 p1 p2 VS 0.25` expanded
still pointing at `VS` while the source became `X1.VS`:
`unknown controlling branch 'VS'`. `raw_params[0]` is the controlling element
for exactly those two device letters, and is now prefixed with them.

Checked standalone (100 V, 4:1, 10 Ω → 25.0000 V, 0.625 A, 62.5 W both sides)
and then inside the LLC, where it reproduces the inline version to the
millivolt.

### The schematic, redrawn

The rectifier is two legs. Each return has its **own** ground symbol — with one
shared symbol every return is a separate wire to the same point and the router
draws them as a ribbon of parallel lines across the sheet, which is most of
what made the old figure unreadable. And the bleeders stay: I expected an ideal
diode's 1e-9 S off-state to define the floating secondary and tested it —
without them the output is 43.4 V with 25 V ripple instead of 48.5 V with 0.12 V.

## 2026-11-12 (night) — the LLC article, and what writing it found

**Branch:** `chore/general-simulator-only` — commit `7ca659f`
**Article:** `docs/articles/simulating-an-llc-converter.md`

A newcomer-level walk-through: configure the extension, derive the LLC gain
law, build the converter, simulate, and compare against theory. Written as a
test of the tool as much as of the writing.

### It works, and the agreement is the right shape

| $f_n$ | FHA | simulated | error |
|---|---|---|---|
| 0.80 | 53.61 V | 54.56 V | +1.77% |
| 0.95 | 49.70 V | 49.67 V | **−0.06%** |
| 1.00 | 48.80 V | 48.55 V | −0.52% |
| 1.30 | 45.31 V | 43.36 V | −4.30% |

Smallest at resonance, growing in both directions — the textbook limitation of

Also verified: ZVS from the sign of the tank current at turn-on (−1.178 A);

1. **`auto_arrange` is not presentable** for circuits with heavy ground
   fan-out — long crossing wires, scattered parts. The figure is hand-placed.
2. **A dependent source's value label collides with its own symbol** (the CCCS

3. **Declared parameter defaults are rejected as missing.** The catalogue

5. **A floating rectifier secondary needs bleeders**, and fails as a singular

## 2026-11-12 (end of day, later) — one domain vocabulary, and ten blocks that had the wrong one

**Branch:** `chore/general-simulator-only` — commit `e6b1a0d`

The two engine-side gaps reported in the previous entry turned out to be one
front-end bug and one contract defect, both fixable here.

### The bug

`inferDomain` existed twice — in `library/insert.ts` and in
`inspector/ComponentParamsPanel.tsx` — and the copies had drifted. Both
guessed a placed block's domain from its first port, then from
`behavior.domain`. Neither read `metadata.domain`, the field the engine
declares and the schema requires.

Measured against the engine's 239 components, the guess disagreed with the
declaration for **ten**:

| component | declared | guessed |
|---|---|---|
| `converter.sig2phys` | mixed | physical-electrical |
| `converter.phys2sig` | mixed | signal |
| `physical_translational.sensor.{force,position,velocity}` | physical-translational | physical-signal |
| `physical_electrical.semiconductor.photodiode` | physical-electrical | physical-signal |
| `hierarchy.subsystem.{enabled,triggered}` | mixed | signal |
| `routing.bus_{assignment,creator}` | signal | signal-bus |

Every one straddles two domains — precisely when a first-port heuristic must
fail, because no single port speaks for the block. That is why the block
declares a domain of its own. One `blockDomainOf` now, reading the
declaration; the port fallback survives only for a component that declares
none, and `behavior.domain` is not consulted at all.

This was never going to fail a test: domain drives wire colour, port symbols
and the causal/acausal split, so a wrong one draws a sheet that misstates the
connection rather than breaking.

### The contract defect

Three vocabularies for one concept:

- a block's `domain` had no enum of its own — it `$ref`s `PortKindDomain`
- `PortKindDomain` accepted `physical-electrical` *and* `electrical`,
  `physical-thermal` *and* `thermal`, plus `mechanical` and `event`
- `behavior.domain` is a third enum entirely

`mechanical` is the one that cannot be translated: it collapses
`physical-rotational` and `physical-translational`, and every bridge resolved
it to translational, so the 13 rotational components lost their domain
wherever that path ran. The short spellings are now illegal — nothing used
them, and all 239 components still satisfy the tightened schema. `v2Domain`
and the identity port pass it fed are gone.

`behavior.domain` keeps its short vocabulary because the engine emits it, but
nothing in the front end reads it for a domain now. **Unifying it is a
gsim-core change and is still open.**

### Verification

13 new tests, including one that walks the whole engine catalogue and asserts
`blockDomainOf` agrees with every declaration. Frontend 1279 passed;
typecheck, biome, check-invariants clean.

## 2026-11-12 (later still) — general-simulator is the only backend

**Branch:** `chore/general-simulator-only` — commit `b8cb880`
**Recovery tag:** `archive/python-compiler`

### The decision

The backend is general-simulator. The front end draws the schematic and owns
it; the engine submits the catalogue of what it has; gsim-core compiles the
document to a netlist; general-simulator solves it; the app displays the
result. That is the whole contract, and everything serving a different
backend is outside it.

### Why so much Python was here

An earlier design had this repository *be* the simulator. Every component
carried an `equations.py`; those lowered through ir1 → ir2 into either a
SciPy state-space problem or a SPICE netlist for ngspice or Xyce. That
design needed a second block taxonomy maintained by hand beside the
engine's, which is where the 26 + 11 disagreements measured in the previous
entry came from. The split was in the wrong place: a component's behaviour
belongs to the engine that solves it, not to the app that draws it.

442 tracked `.py` → 128. What is left is not a simulator:

| | |
|---|---|
| `apps/kernel-sidecar` (46) | the runtime bridge. A webview cannot spawn a process or call a Rust library, so the extension spawns `python -m kernel_sidecar`, which speaks the IPC protocol, calls `gsim_py` to compile, runs the binary and streams waveform chunks back. |
| `packages/simulator` (37) | load/validate a `.gsim_sch`, flatten it, resolve goto/from, compile via `gsim_py_netlist`, run the binary, parse its CSV, write results. Plumbing, not solving. |
| `packages/gsim-model` (19) | the `.gsim_sym` component format and schematic layout geometry. |

It is Python rather than TypeScript because `gsim_py` is a Python binding to
the Rust core. A Node binding, or a JSON CLI on gsim-core, would let the
sidecar be Node and the Python disappear entirely.

### Removed

`packages/blocks` (265 `metadata.yaml` + 234 equation modules),
`packages/engine-xyce`, the ir1/ir2/SciPy/SPICE pipeline and every `*_lower`
pass, `dim_propagate`, `dae_system`, `mna/`, `statespace/`, `behavioral/`,
`symbolic/`, `equation_templates/`, `selection/`, the ngspice/Xyce/SciPy
solvers, and the raw-`netlist` + `solver=` request paths whose only purpose
was reaching them. `simulate.py`'s four-way dispatch is one path.

598 files, −36,345 lines.

### Two things the cut got wrong at first, both caught by tests

- `goto_from_resolve` was deleted with the compiler. It is schematic
  routing, not compilation — `gsim_model.connectivity` needs it. Restored.
- `gsim_model.catalog` read port geometry from `packages/blocks`. Rewritten
  to read `gsim_py.catalog()`, whose entries carry `symbol.bbox` and
  `ports.{inputs,outputs}[].{id,side,offset}` in the same shape. A
  `blocks_root` override stays for an *authored* component directory, which
  no engine knows about yet.

### Verification

Python 296 passed / 2 failed — the same two that failed before this branch
(`test_smoke_e2e`, `test_xfail_circuit`), and **no xfail left**: 73 of them
were "not yet implemented" markers on modules now simply gone. Frontend
1271 passed. ruff, ruff format, mypy, biome, check-invariants clean.
`uv sync --all-packages` resolves after dropping `blocks` from the
`simulator` and `synthesis` dependency lists.

Note: `uv sync` uninstalls `gsim_py` and `gsim_tools`, which are
hand-installed rather than locked. Pre-existing, not caused here, but it

### Still legacy, not touched here

`apps/frontend/src/inspector/device-models.ts` is ~1,700 lines of ngspice

## 2026-11-12 (later) — the old catalogue is not dead, and the numbers say how far it has drifted

**Branch:** `chore/remove-the-dead-catalog` — commit `d7a9403`

### What was asked

Remove the old catalogue. It is superseded by `engine-catalog.json` and is
exactly the kind of leftover that makes a later session pick the wrong
source of truth — the same failure mode as the two GUI repos.

### What was found, and the correction that matters

It is not dead. The front end no longer reads it, which is what made it
look dead, but `packages/blocks/**/metadata.yaml` is still a **runtime**
input to the Python compiler in two places:

- `compiler/dim_propagate.py:95` builds `blocks_root / path_part /
  "metadata.yaml"` and reads `port_sigs` off disk to seed signal-dimension
  propagation. For any block, not only the ones with `equations.py`.
- `equation_templates/loader.py` reads `behavior.equation_template` for the
  91 directories that do have an `equations.py`.

Deleting the 174 "catalogue-only" directories took the Python suite from
**3 failed / 709 passed to 256 failed / 448 passed**. The deletion was
reverted.

Method note, because it caused the wrong call: the grep that "proved" only
tests read `metadata.yaml` was piped through `head -25` and returned
exactly 25 lines. `dim_propagate.py` was the 26th. A truncated search was
read as a complete one. Searches that decide whether something can be
deleted get counted, not skimmed.

### The drift, measured

Comparing `gsim_py.catalog()` against the 265 YAML files, every YAML block
exists in the engine (0 missing) — but the two disagree:

- **26 blocks** have a different `behavior.equation_template`
- **11 blocks** have different `port_sigs`
- 67 YAML carry `port_sigs`; the engine carries 56

So the GUI and the Python compiler are today describing 26 blocks
differently. That is the drift the one-catalogue decision exists to end,
and it is already real rather than hypothetical.

### What was removed

Only what is unambiguously dead, each verified in isolation against the
baseline:

- `simulator/catalogue/` — scans `*_ideal.py` / `*_behavioral.py` /
  `*_spice.py` and builds a registry no production code imports. Its only

- The first loop in `equation_templates/loader.py` — walked 174 YAML files
  per load to reach a `logger.debug` call and nothing else.

After: 3 failed / 701 passed, the same three pre-existing failures.

### What it will take to finish

The engine already carries all three fields the Python side needs
(`equation_template` and `state_count` for all 239, `port_sigs` for 56).
So the end state is reachable: point `dim_propagate` and the template
loader at `engine-catalog.json`, then delete the YAML. The blocker is not
plumbing, it is the 26 + 11 disagreements — each needs a decision about
which description is correct, and that is engine semantics, not a refactor.

### Also still open

- `simulator-compat.ts` hand-lists 59 types inline while
  `engine-capabilities.json` carries 61 generated from the engine.
- `gen-engine-catalog.mjs` does not validate the engine's submission
  against the block-metadata schema, so the contract is unenforced.

## 2026-11-12 — a subsystem's ports follow its body, and the render gate was not a gate

**Branch:** `feat/subsystem-ports-follow-the-body` — commits `7448510`, `21416e3`
**Issue:** #44

### What was asked

Make the parent-side subsystem block reconstruct its input and output ports
automatically when the body changes, and make boundary ports easier to see:
they were small and thin next to real components and hard to pick out.

### What was found

Two bugs, the second hiding the first.

`syncSubsystemPorts` was only ever called at `Ctrl+G`. After the group was
formed nothing re-derived the ports, so a boundary port added, renamed or
deleted inside the body left the parent block unchanged — the sheet looks
right and no longer connects.

Underneath it, `setParam` resolved block ids against `document.model` only.
Editing a port's `id` or `kind` from inside a body therefore did nothing at
all, so there was no rename for the sync to propagate even if it had run.
Fixing only the first bug would have shipped a sync with nothing to sync,
and it would have looked correct in any test that built the document by
hand instead of going through the store.

### What was done

`setParam` is hierarchy-aware, with a root fallback so a root block stays
editable by id while the user is inside a body. `mutateModelAtPath` calls
`syncAncestorSubsystemPorts`, which walks the path deepest-first so a
two-level edit settles in one pass. Parent wires follow a renamed port by
its `boundary_block` identity and are dropped when the port goes. 11 tests
in `subsystem-ports-follow-body.test.ts` pin the wiring rather than the
derivation, including the store paths that were the actual break.

Artwork: marks take a 1.6x stroke (`MARK_SW` ≈ 3.07 against `SW` = 1.92),
leads stay at wire weight, and the causal flag is filled in its domain
colour. Height could not grow — the 200x40 bbox and the port offset come
from `engine-catalog.json`, which is generated from `gsim_py.catalog()`
behind a CI drift gate, so a taller boundary port is a gsim-core change
first. Width and weight were the free axes.

### The gate that could not fail

`scripts/render-schematic.mjs` is the tool invariant 6 names, and it never
built anything — `vite preview` serves `apps/frontend/dist` off disk. The
bundle on disk was from 2026-11-09. Three renders of a changed symbol came
back byte-identical, and the PNG was read closely and judged ("the lead is
too heavy, a lead is just a wire") — a judgement about code that was not in
the picture. The conclusion happened to be right, which is worse: it means
the procedure can be followed exactly and still certify nothing.

The same run exposed a second bug. The script hung after writing its PNG,
for twenty-five minutes, with no output. `pnpm` is not the server: it spawns
`sh -c vite preview`, which spawns the node process that binds the port.
Killing the pnpm pid orphaned that grandchild, which held the port and the
script's stdio pipes — so the process never exited, and the next render
silently reused the stale server it had left behind. That is why the hashes
kept matching.

Both fixed in `21416e3`: unconditional build before serving (~4s warm,
`--no-build` to opt out), preview spawned detached and the whole process
group signalled. End to end 13s, exit 0, port released.

### What's left

- The in-webview schematic search (`apps/frontend/src/search/`, plus the
  `App.tsx` and `app.css` wiring) is **uncommitted on this branch**, pending
  a decision: invariant 0 forbids an in-webview search panel, and the
  `ActivityRegistry` id union still reserves `core.search`. VS Code's Ctrl+F
  cannot reach into a webview canvas, so searching a *schematic* is not
  something the host provides — but that is the user's call, not an agent's.
- `simulator-compat.ts` still hand-lists 59 engine types as inline data
  while `engine-capabilities.json` carries the same fact generated from the
  engine. Two sources for one answer; the generated one should win.
- `packages/blocks/**/metadata.yaml` (265 files) is no longer read by the
  front end but is still in the tree, and `catalog.test.ts` still validates
  against it.

## 2026-11-05 (later) — rendering made grid-exact, a .vsix that installs, and a Python front end

**Branch:** `main` — commits `44f75d3`, `b689edf`, `120b291`

### Rendering

Every fix in `44f75d3` was found by rendering the buck converter and looking
at it, not by a failing test. The root cause of most of the geometry defects
was one thing: `SYMBOL_SCALE` 1.6 and `STUB_LEN` 16 against a `GRID` of 20,
so a port centre landed at 32 and a two-terminal part spanned 128 — nothing
on grid, ever. At scale 2 with a one-grid lead the arithmetic closes and
every terminal sits on an intersection. `wire-path.ts`'s six-pixel
`ORTHOGONAL_TOLERANCE_PX` and `snapNearOrthogonal` exist to hide the old
mismatch and can probably go now.

`STUB_LEN` was declared twice — `Port.tsx` draws the lead, `port-hit-test.ts`
decides where the wire attaches to it — and I changed one of them before
noticing, which would have put every wire four units short of its lead.

Junction dots were computed from waypoints only, which misses both real
cases: three wires meeting at a shared port (no wire has three vertices
anywhere) and a wire bending onto another's segment, which is how a rail is
tapped.

`examples/buck_converter.gsim_sch` is the reference sheet. Writing it
exposed that the canvas drops a wire naming a non-existent port in silence —
the diode's pins are `a`/`k`, the generator said `p`/`n`, and the render came
out missing its freewheel path. Now issue #2.

### The .vsix

Renaming the manifest changed the extension id and broke the integration
suite, which had the old literal in three more places. Centralising it
uncovered a nastier bug: `getTestApi` held its result in a local called
`exports`, and this file compiles to CommonJS where a module-level
`export const` is emitted as `exports.NAME` — so every reference to
`EXTENSION_ID` resolved to that local and hit its temporal dead zone.

`pnpm package` now builds, bundles the webviews into `media/frontend` (the
only root `webview-content.ts` probes that survives `vsce package`) and
writes the .vsix. Verified: it installs via `code --install-extension` into
an isolated extensions dir, and the integration suite passes against a real
VS Code 1.145.0 — **14 passing**. The kernel sidecar reaches `KERNEL_READY`
via `uv run --project . --package kernel-sidecar`.

### The port-domain bug

Generating the same buck converter through the new Python package produced
grey wires where the hand-written sheet produced black. Cause: 136 port
declarations across 55 metadata files said `kind: { domain: electrical }`.
That is `behavior.domain`'s enum, not `PortKindDomain`'s, where the value is
`physical-electrical`. Both fields are called `domain` and sit a few lines
apart in the same file, and nothing validated it — about a fifth of all
electrical parts drew in the unknown-domain grey and failed port-compatibility
against correctly-spelled parts. Fixed at source, manifest regenerated,
`catalog-port-domains.test.ts` added as the guard.

Worth noting how this was found: not by reading the metadata, but because an
independent implementation disagreed with the first one.

### Python front end

`general-simulator-python` (local, not yet pushed — repo creation was
blocked). `gsim.geometry` mirrors this repo's geometry contract exactly, and
the buck converter it generates renders identically to the hand-authored one.
It refuses what this canvas accepts and then draws wrongly: unknown port,
off-grid placement, overlapping bodies, diagonal wires. A real RC step
response through the engine matches `10*(1-exp(-t/RC))` to four figures.

### Rendering: a harness, and a first honest look

The user's primary complaint is that schematics render ugly. The checked-in
evidence (`docs/circuit_test/buck_converter/frontend_buck_schematic.png`,
June) shows diagonal wires, hairline strokes and stray stubs — but that
image is five months old and several fixes behind, so it is not evidence
about today's code.

`scripts/render-schematic.mjs` was written to end that problem: it boots the
Vite preview, drives the harness through `__gensim_load_document` and
`__gensim_canvasFitView`, and writes a 2× PNG of the canvas. Rendering
quality cannot be unit-tested — no assertion sees two overlapping labels —
so the rule (AGENTS.md invariant 6) is that rendering work is not done until
someone has looked at the output.

Rendering the buck converter on current code shows real progress since June:
**wires are orthogonal, strokes are firm and dark, junction dots are drawn.**
What is still wrong, from the render:

1. Terminal leads are far too long, so components float apart from the
   circuit instead of sitting in it. `Port.tsx`'s `STUB_LEN = 16` is in
   *screen* units, outside `BlockSymbol`'s `scale(SYMBOL_SCALE = 1.6)` —
   the two unit systems are not reconciled.
2. Pin names (`p`, `n`, `c+`, `c−`, `A`, `K`, `+`, `−`) are drawn on every
   terminal. A finished schematic never shows pin names on two-terminal
   passives.
3. Value labels sit far from their symbols — `100 µH` floats in open space —
   because `labelAnchorFor` anchors to the bbox, which is much larger than
   the drawn glyph.
4. No reference designators (`V1`, `L1`, `C1`, `R1`, `D1`).
5. The dotted grid is visually noisy at render density.
